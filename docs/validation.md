## 验收顺序

1. 后端 echo 模式，真实 C3 上执行 1 MiB 和持续流传输，比较 SHA-256，记录最小剩余 heap。使用 `hardware_probe.py --stream` 测连续流；默认模式逐块等待往返，不代表单向吞吐极限。
2. UxPlay 直连作为对照；C3 广播真实 TXT 后，通过 C3 完成 AirPlay 连接。
3. 检查 SETUP 的时序、视频与音频端口，以及 C3→后端和后端→手机的字节计数。
4. 持续至少 5 分钟的屏幕变化，不将静态连接存活等同于画面持续更新。
5. 打开 AssistiveTouch，确认 move/click/key 的真实效果，再并发视频。
6. 接入截图适配器和 Agent，明确停止/释放输入机制后测试任务。

仅公开不含 Wi-Fi、token、手机截图、设备 MAC 或完整备份的测试结果。

## macOS 发现冲突

首轮实际收到的画面曾绕过 C3：iPhone 将相同身份的 upstream 和 C3
广播合并，直接经 IPv6 连接 Mac。当时 C3 通道为零、字节计数不增长。
这次对照不计入 C3 视频成功。修复后 upstream 通过本机 Bonjour LocalOnly
发布，发现脚本用原生 DNS-SD 读取真实 TXT，再交给 C3 广播；随后 C3 上行
持续增长，UxPlay 的两个 TCP 连接对端均为 127.0.0.1。

BLE 配对验收必须检查安全会话和真实画面响应。普通 GATT 连接、订阅成功或
`POST /hid` 返回 `ok` 都不足以证明 iPhone 已接受鼠标键盘。

一次手机“搜索不到”发生时，Mac 实扫仍收到可连接的 C3 AirBridge HID 广播；
用户在 iPhone 设置内重启蓝牙后恢复发现并完成安全配对。没有为此更改硬件
地址或清空整个 NVS。后端另修复了 CLOSE 后在途数据、突发数据调度和临时
`/info` 控制连接关闭时误伤视频的问题，并分别加入回归测试。

## 输入验证的观察方式与边界

最初仅看 AirPlay 画面和 HTTP `ok`，没有观察到界面响应；后来读取 iPhone
的系统日志，确认 BackBoard 的鼠标坐标确实随 C3 指令变化。随后用 USB
开发者截图做诊断，截到实际圆点、返回操作后的页面和计算器 `579`。
计算器由 USB 启动，算式按键来自 C3 BLE HID；USB 截图只证明输入效果，
不计入 C3 视频转发成绩，也没有替代 `/frame` 的过期拒绝机制。

HID 兼容调整包括一致的 GAP 设备名/键盘 appearance、50 ms 键盘按下时间，
以及把 ESP-IDF 6.0.1 的 External Report Reference 从 Battery 服务 UUID
`0x180f` 修正为 Battery Level 特征 UUID `0x2a19`。后者用链接包装器实现，
不修改全局 SDK；尚未单独 A/B 证明哪个调整导致兼容性改善。

后续模型计算器测试已补充了 C3 画面与输入的真实决策闭环。运行时配置可选
USB 备用截图，画面来源明确标注，不能拿 USB 截图冒充 C3 视频。

维护时曾通过已信任的 USB 开发者接口打开系统蓝牙设置页，帮助诊断连接；
没有用 USB 注入点击、按键或剪贴板。日常 Agent 的 USB 适配器仅截图。

## 本轮断流修复及证据边界

- 后端关闭通道时取消反向 UDP 泵、删除端口映射；12 次反复创建/关闭回归测试确认任务数量不增长。
- C3 识别有限的已关闭通道在途数据，避免与 CLOSE 交叉时重置整个隧道；状态新增重连、最低内存和最大空闲块。
- 上游 UxPlay 视频 EOF 路径补丁已编译，关闭旧 socket 并复位连接。代码路径修复不等同于新版已通过长时间视频实测。
- 静态 AirPlay 页面可能不发送新帧。原先 1 单位鼠标移动可能不足一个像素或卡在边缘，改为小幅往返移动后要求真实新 JPEG。监督进程不单凭旧帧重启；只有持续大量媒体流入而解码仍停止才自动复位。静态与解码停止两种情况均有回归测试。
- 固件限制 Wi-Fi 动态缓冲，并修复 BLE 安全状态竞态。新版本仍需要解锁后的连续视频负载与断流恢复验收。
